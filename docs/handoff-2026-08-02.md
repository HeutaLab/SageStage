### The export 🟠, already scoped so nobody repeats the analysis

`export.js` fills `shots[]` with every screen's canvas before any writer runs.
The writers *do* release as they consume, so the peak is at the end of the render
loop — roughly 1 GB for a 30-screen deck at 2×, on a teacher's laptop.

The fix is well-defined: all three writers need only a raster plus dimensions
(`writePngs` a PNG blob, `writePdf` a JPEG dataURL, `writePptx` the raster plus
`canvas.width/height`), and the chosen format is known *before* rendering starts.
So rasterise each screen to the writer's format immediately, release the canvas,
and hand the writers blobs.

Not done because the defect is a memory peak, and a memory fix nobody has watched
a real 30-screen export survive is a claim rather than a fix.

## 5. Known limitations in what shipped today

State these plainly rather than discovering them later.

- **Nothing from either session is tested on Tauri.** That covers the storage and
  cross-tab work — both `storage.js` changes (the close-time flush,
  `hasPending()`) and the adopt path, where the file backend has different
  `dirty` semantics and syncs windows by another route — **and now the P0 work
  too**. Two P0 pieces specifically depend on the webview: the CSP is a `<meta>`
  in `index.html` that Tauri will want in its own config, and `sameOrigin()`
  decides whether an iframe is handed `allow-same-origin`.
- **Export is verified at the mechanism level only.** The blob Worker starts
  under the new CSP and `importScripts` loads JSZip, which was the CSP risk. A
  real 30-screen export has still never been watched — that is the separate
  session the memory 🟠 below is waiting for, and it is now the *only* thing
  standing between that fix and being done.
- **The multi-tab conflict is unresolved by design, not fixed.** When both tabs
  edit at once, one edit is lost. It now loses the *right* one (the tab being
  typed into wins) and says so in the code. Converging both needs per-field
  merging with timestamps, which does not exist here. Retrying a declined payload
  cannot work: by then our own write has replaced it in storage, so re-adopting
  would revert the local edit.
- **Focus is not preserved across a rebuild that genuinely is needed.** The work
  stops the needless rebuilds; it does not make the necessary ones painless.
- **Widget geometry persists its clamp once the teacher interacts** — see the
  decision above.
- **`.wbtn` is fixed but poll vote and name-chip-× are not** — same question,
  unasked.
- **Dashboard list add/remove still drops input focus** on its full re-render.
  Only the diacritic half of that finding is done.

## 6. Working notes for whoever picks this up

**The checklist is a set of leads, not a set of defects.** Four findings today
turned out to be already fixed or materially wrong about their own cause — the
Base 10 `d >= 3` guard was long gone, `prefers-reduced-motion` had two thorough
blocks already, and the corrupt-JSON item claimed `load()` fails by throwing when
mostly it returns null without throwing (a try/catch-only fix would have missed
the commoner path). **Read the source before patching.** Line numbers have
drifted badly; the storage layer moved out of `app.js` entirely.

**Verifying is where the time goes, not editing.** Each fix costs a seed, a test,
a restore and a re-verify. Budget accordingly.

**Two hard-won testing lessons:**

- Back up state in the tab you are *not* writing to. Proving the cross-tab
  clobber fix meant writing a sentinel over the live state; it was recoverable
  only because the second tab still held the real state in memory. With one tab
  open that would have been a restore from snapshots.
- **Widget ids and coordinates settle questions that deck-level counts cannot.**
  A count that looks wrong is usually a debounced write landing between two
  reads. Check ids before raising an alarm.

**Test fixtures need a real screen shape.** Hand-built screens missing a
`background` crash `applyBackground`. Clone an existing screen instead.

**Three more from the P0 session:**

- **A passing test can pass for the wrong reason, and a security test that does
  is worthless.** The check that the retyped blob no longer executed HTML passed
  — and so did the control on the *unfixed* path, because the CSP was catching
  the payload before the retype ever mattered. Two defences had been added and
  the test could not tell which one was working. Isolating it meant checking
  `blob.type` rather than whether script ran. **Confirm the mechanism, not the
  absence of the symptom.**
- **A hostile fixture served through the real path beats a unit test**, and by
  more than expected. Putting a deliberately nasty template behind a local
  template source exercised the importer, the vetting dialog, storage, and every
  widget's mount in one click — and it was the *rendered* result that showed the
  spoofed YouTube host had become a plain `<video>` with no iframe at all.
- **Allow-list at the sinks, deny-list in the sweep.** Getting that the wrong way
  round is not theoretical: the first version of the deep scheme walk blanked
  `"Note: bring a coat"` and `"Learn about javascript: in year 6"` — an agenda
  entry and a Year 6 lesson. Anything that inspects arbitrary teacher text has to
  assume the text is innocent until a scheme is hostile *by name*.

**And the line-number warning above held.** Every `file:line` the P0 items quoted
was wrong by hundreds of lines. The checklist is a set of leads.
